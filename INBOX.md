# Bug report inbox

Endpoint for reports sent by the Sifu Moveset Editor's **Report a bug** dialog, plus a
password-style admin page for reading them.

| | URL |
| --- | --- |
| Report intake - where the app POSTs | `https://charlestiudev.qzz.io/api/inbox/report` |
| Inbox - the admin view | `https://charlestiudev.qzz.io/admin/reports` |
| Unlock link - issued on rotation | `https://charlestiudev.qzz.io/admin/unlock?k=<token>` |
| Site | `https://charlestiudev.qzz.io` |

- Intake: `POST /api/inbox/report` (JSON, no client auth - see *Abuse model*)
- Admin: `/admin/reports`, unlocked by a tokenised link
- Storage: Cloudflare D1 binding `DB`, migration in `migrations/`
- Retention: 180 days, purged opportunistically as reports arrive

The client half of this contract is `Core/BugReport.cs` in the editor repo: `Endpoint`
holds the intake URL above, and `SendEnabled` gates the Send button in the dialog.

## Setup

One-time, in order. Kept manual on purpose: `wrangler secret put` never reads a value
back, so a token generated by a tool and not shown to you is a token you cannot recover
from. Choose the value, write it down, then send it.

### 1. Create the database

Cloudflare dashboard -> Storage & Databases -> D1 -> Create database ->
`portfolio-inbox`. Copy the id it gives you.

### 2. Paste the id into `wrangler.jsonc`

Replace the placeholder with the real id. While the placeholder is present the build
succeeds and the deploy fails on the binding with
`binding DB of type d1 must have a valid database_id specified [code: 10021]`.

### 3. Apply the migration

```bash
npx wrangler d1 migrations apply DB --remote   # needs npx wrangler login
```

Or open the database in the dashboard -> Console and run the contents of
`migrations/0001_inbox.sql`. The migration is idempotent, so re-running it is safe.

### 4. Set the bootstrap token

Pick a long random value and save it in your password manager **before** the next
command: Cloudflare stores it encrypted and it cannot be read back.

```powershell
$t = '<your token>'
$t | npx wrangler secret put ADMIN_TOKEN
```

`wrangler secret put` takes the secret *name* only - the value arrives afterwards. With
no terminal attached (a redirected or agent shell) the prompt aborts with "cannot be run
in a non-interactive context", so pipe it as above. The dashboard works too: Workers &
Pages -> `charlestiuportfolio` -> Settings -> Variables and Secrets -> add an encrypted
`ADMIN_TOKEN`.

### 5. Wait, then verify

The secret lands in a new Worker version, which takes a few seconds to take over
traffic. Probing too early returns the same 404 as a wrong key, which reads as a bad
token:

```powershell
Start-Sleep 20
curl.exe -sS -o NUL -w "%{http_code}`n" "https://charlestiudev.qzz.io/admin/unlock?k=$t"
```

`303` means the token is live. `404` means it is not (yet): wait another 30 seconds and
try once more. Do not hammer it - the route allows **10 unlock attempts per hour per
IP**, and every attempt counts, including successful ones.

### 6. Claim the unlock link

Open `https://charlestiudev.qzz.io/admin/unlock?k=<token>`, press **Rotate link**, and
save the URL it prints. It is shown exactly once, and it replaces `ADMIN_TOKEN` as the
credential from then on.

## Deploying

Pushes to `main` deploy through Cloudflare's git integration, so a commit is a deploy.
Nothing here needs `wrangler deploy`.

### Build command

Cloudflare runs `npx @opennextjs/cloudflare build` (configured in the dashboard, not in
`package.json`). The app is on Next.js 16, which OpenNext supports, so no flags are
needed. If a future Next upgrade lands outside its support window,
`@opennextjs/cloudflare` fails the build on purpose - upgrade rather than reaching for
`--dangerouslyUseUnsupportedNextVersion`.

## Verifying a deployment

Against `https://charlestiudev.qzz.io`:

| Check | Expect |
| --- | --- |
| `GET /` | 200 - a 1101 or 500 here means the Worker itself is failing |
| `GET /api/inbox/report` | 405 - the route exists and wants POST |
| `POST /api/inbox/report` with a malformed body | 400, not 500 |
| `GET /admin` before setup | 200 with "Inbox is not set up yet" |
| `GET /admin` after setup, no cookie | 404 |
| `GET /admin/unlock?k=<current>` | 303 to `/admin/reports` |
| `GET /admin/reports` with that cookie | 200, header chip shows link age |
| `npx wrangler secret list` | contains `ADMIN_TOKEN` (names only, never values) |
| `npx wrangler d1 execute DB --remote --command "SELECT name FROM sqlite_master WHERE type='table'"` | `reports`, `report_notes`, `rate_limits`, `settings` |

## Unlocking and rotating

The credential is a 256-bit token in a URL. Only its SHA-256 is stored, so the link
cannot be recovered from a database dump - it is shown exactly once, when rotated.

| Setting | Key in `settings` | Meaning |
| --- | --- | --- |
| Rotated token hash | `admin_token_hash` | Set by **Rotate link**; supersedes `ADMIN_TOKEN` |
| Token expiry | `admin_token_expires_at` | 30 days; the header chip counts down |
| Session key | `admin_session_key` | HMAC key for the session cookie |
| IP salt | `ip_salt` | Salt for the hashed reporter IP |

The session cookie is `HMAC-SHA256(admin_session_key, "inbox-session-v1")`, scoped to
`/admin`, `HttpOnly`, `Secure`, `SameSite=Strict`. Because it uses a separate stable
key, rotating the unlock link does **not** sign the browser out.

**Break-glass** - lost link, or the 30-day expiry hit. Delete the stored hash so the env
token becomes authoritative again:

```bash
npx wrangler d1 execute DB --remote --command "DELETE FROM settings WHERE key IN ('admin_token_hash', 'admin_token_expires_at')"
```

If the env token is unknown too, set a new one and follow *Setup* from step 4. The hash
cannot be reversed, so a lost link is always re-issued, never recovered.

## Abuse model

The app ships as an exe, so no key baked into it can be secret. Defence is server-side:

- three fixed-window counters per report: 5/day per client id, 20/day per hashed IP,
  200/day globally (counters live in `rate_limits` and expire);
- a hidden `website` field - a bot that fills it gets a fake success and writes nothing;
- hard caps: 1 MB request, 256K characters of log, 8K characters of body;
- only a salted truncated hash of the reporter IP is stored, never the address;
- the unlock route rate-limits attempts to 10/hour per IP and answers a wrong key with
  the same 404 as a route that does not exist.

## Local development

```bash
npx wrangler d1 migrations apply DB --local   # once
npx next dev -p 3123                          # .dev.vars supplies ADMIN_TOKEN
```

`.dev.vars` is gitignored and never committed; any value works there, because it is only
ever compared against the local database.

`npx opennextjs-cloudflare preview --port 8791` runs the real Worker in `workerd`, the
closest local analogue to production. Local D1 state lives under `.wrangler\state`,
keyed by `database_id`, so changing that id starts from an empty database.

Two Windows notes: the origin check compares hosts exactly, so browse
`http://localhost:8791` rather than `127.0.0.1` when testing a rotate (a mismatch is a
403); and only one preview may run at a time - two `wrangler dev` sessions sharing
`.wrangler\state` hang every request, including `/`.

The editor redacts before anything leaves the machine: `C:\Users\<name>` becomes
`<user>`, and the content/output roots become `<path>`.
